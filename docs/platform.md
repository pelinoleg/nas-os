# Платформа: сервер, отдача, расписания, события

_История и подробности. Открывай, когда правишь HTTP-слой, отдачу статики, планировщики, каталог событий, сессии._
_Правила и грабли, которые важны ВСЕГДА, живут в `CLAUDE.md` — здесь только детали._

**Отдача статики: панель годами слала 1.39 МБ НЕСЖАТЫМИ на каждую загрузку (2026-07-27).**
Вопрос пользователя «desktop.html 1.3 МБ, ничего не оптимизировано, как это будет работать» —
по делу, и первая же проверка заголовков это подтвердила: `Content-Length: 1386961`, никакого
`Content-Encoding`. Хуже: оболочка намеренно `no-store` (мобильные держали стухший shell), то
есть ПОЛНЫЙ мегабайт качался при КАЖДОМ открытии панели. Лечение — gzip в `_static` с кэшем
сжатых копий по ключу (путь, mtime, размер): 1386961 → 401228 Б (29 %, в 3.5 раза меньше),
`tui-editor.js` 534 → 158 КБ. Сжимать на каждый запрос было бы ~80 мс CPU Pi на хит, поэтому
кэш; он ограничен 48 записями (набор файлов фиксирован). ГРАБЛИ, которые надо было учесть:
(1) сжатое тело — ДРУГАЯ сущность, поэтому ETag получает суффикс `-gz`, иначе клиент может
склеить 304 от одной формы с телом другой; (2) `Vary: Accept-Encoding` обязателен и на 200, и на
304; (3) клиент без gzip (`Accept-Encoding: identity`) обязан получать исходник — проверено;
(4) тело после распаковки должно быть БАЙТ В БАЙТ исходным файлом (`curl --compressed | cmp`) —
проверено. Состав файла (для будущих решений): CSS 284 КБ (21 %), JS 1.10 МБ (79 %), из JS
58 % — HTML-шаблоны в template-строках, 6 % — комментарии, SVG-пути всего 2 %. То есть
«раздутость» — это не мусор, а сам объём приложения; дробить его на модули = крупный риск ради
эффекта, который сжатие уже дало дешевле. ПРАВИЛО: прежде чем оптимизировать РАЗМЕР ИСХОДНИКА,
посмотри, что реально уходит в сеть — заголовок ответа отвечает на этот вопрос за секунду.

**АУДИТ правок 2026-07-27 (расписания, сжатие, наблюдатель версии): 2 настоящие ошибки, обе
исправлены.** Проверялось не «работает ли счастливый путь», а те ловушки, на которых этот бокс уже
горел.
- **ГЛАВНАЯ НАХОДКА — секундного разрешения mtime НЕ ХВАТАЕТ, и это било по самому частому виду
  правок здесь.** Ключ кэша сжатых копий был `(путь, int(mtime), размер)`, ETag — тем же. Скриптовая
  перезапись файла ТОЙ ЖЕ длины внутри одной секунды (ровно то, что делают мои правки: заменить
  символ, поменять число) не меняла ни ключ, ни ETag → доказано экспериментом: панель отдала СТАРОЕ
  сжатое тело, а ETag совпал, то есть перевалидирующий браузер тоже остался бы на старом файле
  (та же семья, что давняя грабля со стухшим i18n.js). Выглядело бы как «моя правка не применилась»
  — и не лечилось бы ни рестартом, ни F5. Лечение: везде `st_mtime_ns` (кэш сжатия, ETag,
  отпечаток `web_stamp`). ПРАВИЛО: любой кэш/валидатор, ключуемый по времени файла, обязан быть
  наносекундным — секунда это вечность для генератора правок.
  ПОБОЧНО о методике: первый мой тест этого НЕ поймал, потому что пробный файл был 208 байт —
  меньше порога сжатия в 1 КБ, и кэш просто не участвовал. Отрицательный результат теста ничего не
  значит, пока не доказано, что тест дошёл до проверяемого кода.
- **Мусор в состоянии планировщика kopia**: удалённое задание оставляло `done[bid]`. Не просто сор —
  НОВОЕ задание с переиспользованным id унаследовало бы «этот слот уже отработан» и тихо пропустило
  бы первую ночь. `_kp_forget_runs` теперь чистит и `done`, и `pending` (проверено ассертом).
- **Проверено и оказалось верным** (13 ассертов): стухшие часы Pi без RTC не заставляют догон
  переигрывать прошлое (защита — «уже был реальный прогон позже слота»); сутки с переводом часов
  дают ровно один слот и в удвоенный, и в несуществующий час, причём метка совпадает с моментом;
  00:00 и 23:59 не срываются на соседние сутки; мусор в расписании (`time:null`, `time:5`,
  `dow:"nonsense"`) не роняет тик. Иконки и классы новой плашки существуют в словаре `svg()` и в
  CSS (проверено отдельно — на этом проект уже спотыкался).

**ГРАБЛЯ CDP-тестов (важно):** headless-chromium репортит `hover:none`, поэтому правила под
`@media(hover:hover)` НЕ применяются и ховер-баг невоспроизводим — запускать chromium с
`--blink-settings=primaryHoverType=2,availableHoverTypes=2,primaryPointerType=4,availablePointerTypes=4`
(в `cdp.py` уже прописано), ховер наводить через `Input.dispatchMouseEvent{type:mouseMoved}`, а
русскую локаль эмулировать `Emulation.setLocaleOverride`. Проверено: 12/12 (вложенность отбита с
объяснением, заметка видна в деталке и на карточке, ноль кириллицы на всех вкладках при ru-RU,
высота строк 30px до и во время ховера).
**Заодно: одна кривая запись в `sessions.json` роняла ВСЮ панель в цикл рестартов.** 26.07 15:55
в файле оказался словарь вместо числа-срока → `_load_sessions()` падал с TypeError на ИМПОРТЕ
модуля, systemd перезапускал панель в тот же креш, счётчик рестартов дошёл до 6. Теперь каждая
запись проверяется по ФОРМЕ (строка-токен + число-срок, `bool` не считается числом), мусор
отбрасывается молча. ПРАВИЛО: то, что читается на уровне модуля, не имеет права бросать — иначе
бокс теряет веб-интерфейс из-за одной строки в файле состояния.

**Панель сама замечает, что вышла новее (2026-07-27).** Раньше открытая вкладка (телефон, второй
монитор, киоск) жила на старом коде, пока кто-нибудь не нажмёт F5 — а правки прилетают на бокс
постоянно. Механизм ОДИН на оба случая: `GET /api/version` отдаёт 16-hex отпечаток всего `web/`
(имя+mtime+размер, stat-only, кэш 2 с, 0.7 мс) и флаг `dev`; в оболочке `versionWatch()`
запоминает ПЕРВЫЙ ответ как базовый и опрашивает раз в 30 с (скрытая вкладка не спрашивает вовсе).
Отпечаток сменился → тихая плашка `.verbar` «вышла новая версия · Reload», САМА панель не
перезагружается никогда: можно быть на середине формы. **Режим разработки:** появился файл
`/etc/nas-os/dev-reload` → опрос раз в 1.5 с и АВТОМАТИЧЕСКАЯ перезагрузка (правишь `web/*` —
страница обновляется сама, F5 больше не нужен). Файла нет ни на одной обычной установке.
Осознанно НЕ SSE: поток держал бы нить на каждую вкладку (ThreadingHTTPServer, Pi), а ответ —
сорок байт. Порядок работ выбирался так, чтобы обрыв на любой половине был безвреден: сначала
коммит сервера (неиспользуемый эндпоинт ничего не меняет), потом клиента (нет эндпоинта или 401 →
`catch` → наблюдатель молчит). Проверено: 12 ассертов в node на подменённых fetch/DOM (базовый
ответ не уведомляет, смена показывает плашку, вторая плашка не копится, dev перезагружает сам,
401/мёртвая сеть/скрытая вкладка молчат) + живой headless-браузер (страница грузится, док на
месте, без сессии плашки нет). ГРАБЛЯ правки: скриптовая вставка разрезала МНОГОСТРОЧНЫЙ
комментарий пополам — хвост «The panel is one big» остался отдельной строкой и дал IndentationError.
Якорь для вставки брать по ПОЛНОЙ строке, а не по её началу.

## Дрель восстановления настроек (2026-08-05)

`settings_backup_drill()` (nas-web.py, рядом с кодом бэкапа настроек): свежайший архив →
распаковка во временную папку (`tarfile filter="data"` — абсолютные пути/побеги отвергаются),
затем каждую подсистему судит ЕЁ ЖЕ инструмент: `testparm` для smb.conf/nas-shares.conf,
`docker compose config -q` для каждого стека (cwd = папка стека, чтобы подхватился .env),
магия `TDB file` для passdb, парсеры для json/rclone.conf/config.xml, PEM-заголовки для ключей.
Живой бокс не трогается вообще. SKIP ≠ FAIL (нет инструмента/файла — это не провал).
Результат — `~/nas-config/settings-drill.json` (сам попадает в следующий бэкап), провал —
событие-состояние `sbdrill`. Поверхности: строка+кнопка в Настройки → Settings backup,
`POST /api/settings-backup/drill`, CLI `settings-drill`, месячный `nas-settings-drill.timer`
(2-е число, 04:10, ставит визард в базе). 5 тестов, включая негативный контроль (битый архив
обязан провалиться) и враждебные пути в tar. Проверено на живом архиве от 2026-08-01: OK, 13
проверок; неточность «битый webauth подписан not in archive» поймана негативным контролем и
исправлена (присутствует-но-битое = FAIL, отсутствует = SKIP).
