# NAS-OS — инструкции проекта для Claude Code

Домашняя NAS-система для Raspberry Pi 5: движок настройки + веб-панель в стиле «десктоп-окружения».
Этот файл переживает переустановку (он в git), поэтому `claude`, запущенный в папке репозитория,
сразу знает архитектуру и правила. Память в `~/.claude/` — локальная и при переустановке пропадает;
источник правды по проекту — ЭТОТ файл + история git.

## Что это и где что лежит
Репозиторий: **github.com/pelinoleg/nas-os** (ветка `main`). `gh` авторизован.
- `nas-web.py` (~5000 строк) — **stdlib-only** HTTP-сервер (ThreadingHTTPServer) от **root**, порт 80.
  Отдаёт статику из `web/`, REST `/api/*`, WebSocket `/ws/term`. Мост к движку:
  `bash nas-wizard.sh api <action>` через env `NASW_*`. Никаких внешних Python-зависимостей.
- `nas-wizard.sh` (~2500 строк) — движок+инсталлятор. Интерактивный (whiptail) и headless
  API-режим (`nas-wizard.sh api <action>`, вызывается из nas-web без whiptail).
- `web/desktop.html` — весь десктоп: инлайн `<style>` + инлайн `<script>` (ванильный JS, без сборки).
- `web/setup.html` — мастер первичной настройки (отдельная страница).
- `web/sw.js` — service worker (network-first; HTML — только из сети).
- `install.sh` — `curl -fsSL .../install.sh | sudo bash` → `git clone/reset --hard origin/main`
  в `/opt/nas-os`, ставит службу `nas-web` оттуда. **Переустановка воспроизводит текущий код 1:1.**
  Запускает `nas-wizard.sh api system` = `stage_system_apply` (авто-база, headless). Что база
  ставит из коробки (2026-07-20 расширена): пакеты (STACK/UTIL/PI + docker + gh), watchdog,
  uas-off, usb-timeout, smartd-guard, thumbs-таймер, **avahi+libnss-mdns** (`.local`),
  **Samba** (`install_smb_shares` — вкладка Sharing живая, шар ноль), **drivetemp** (темп. SATA),
  notify-helper, motd, **netguard** (сетевая устойчивость — теперь в базе, не в стадии backup)
и **unattended-upgrades** (2026-07-20: авто-security-обновления в базе — бокс без присмотра не
копит CVE; канал только security, тумблер в панели остаётся). Целевая ОС — **Debian/RaspiOS**:
install.sh на другой ОС (Ubuntu) громко предупреждает и спрашивает подтверждение через `/dev/tty`
(пайп `curl|bash` — stdin занят скриптом), headless-обход `NASOS_FORCE_OS=1`. Пакеты, которых
установщик не нашёл в репах (переименование в новом Debian), собираются в
`/var/lib/nas-wizard/skipped-packages` (`report_skipped_packages`, громкая сводка в конце
`api system`; «Pi packages» на не-Pi — ожидаемо, не шумим) → `stats().missing_pkgs`
(dpkg-перепроверка, TTL 5 мин) → несмахиваемая плашка `.basepkgs` внизу стола
(`paintBasePkgs`): исчезает САМА, когда пакеты доставлены, кнопки «скрыть» нет намеренно.
  Дальше — диски/пул/шары/стеки/тюнинг в панели/веб-мастере (железо у всех разное).

## Рабочий цикл разработки
1. Правишь файл.
2. **Питон**: `sudo systemctl restart nas-web` (обязательно — код в памяти службы).
   **Статика** (`web/*`): рестарт не нужен, сервер читает с диска; но браузер/кэш — см. ниже.
3. Проверка: `python3 -m py_compile nas-web.py`, `bash -n nas-wizard.sh`, для JS —
   вынуть `<script>` и `node --check`, для CSS — проверить баланс `{` / `}`.
4. **Всегда коммить И пушить** каждую законченную правку (пользователь может уйти/выключить NAS).
   Подпись коммита: `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.
5. **CLAUDE.md — часть правки, не после.** Любая новая фича/грабля/изменение состояния —
   сразу дописывается в CLAUDE.md (секция «Состояние» и/или «Ключевые грабли») в ТОМ ЖЕ коммите
   или следом, и пушится. Файл не должен отставать от кода: он единственный источник правды,
   переживающий переустановку. Правило пользователя (2026-07-22): держать CLAUDE.md всегда
   актуальным и всё пушить — по умолчанию, без напоминаний.
6. Дев-хост = сам NAS (Pi 5). Служба `nas-web` — `enabled` (стартует после ребута сама).

## ЖЕЛЕЗНЫЕ ПРАВИЛА (нарушение = сломанная переустановка / несогласованный UI)

### 1. Полнота установщика (wizard-completeness)
Любое ГЛОБАЛЬНОЕ изменение системы (udev-правило, systemd-юнит, пакет, конфиг в `/etc`,
sudoers, fstab-логика) ОБЯЗАНО быть прописано в `nas-wizard.sh`/`install.sh`, иначе после
переустановки оно исчезнет. Если правишь «живьём» на боксе — параллельно правь генератор
в визарде. Секреты/конфиги пользователя (пароли, `nas-backup.json`, `desktop.json`, задачи)
в репо НЕ входят — они восстанавливаются из «Настройки → Бэкап настроек» (`_bk_sources()`).
**Что кладёт бэкап настроек**: весь `~/nas-config/` (тема/окна/ярлыки/обои, glance.json,
screen.json, storage.json — выбор основного хранилища, профили и история приложения Backup,
кэш иконок), `etc/nas-os/{webauth,nas-backup}.json` (пароль панели, главный NAS), `etc/nas-wizard/`
(motd, usb-import), Samba (`smb.conf` + `passdb.tdb` — пароли SMB-юзеров), `opt/stacks/*/`
(compose+.env стеков), SSH-ключ push-бэкапов (`/root/.ssh/nas-backup`). `reference/` — только
справочно (НЕ авто-восстановление): `fstab`/`snapraid.conf`/`exports` (диски другие — руками) и
`netplan/*.yaml` (Wi-Fi-пароль/статический IP; секретная секция «Сеть»). Секретные секции
(webauth/nasbackup/network) прячутся за отдельным подтверждением при восстановлении. Дефолтный
путь — основное хранилище (пул или выбранный USB через `storage_root()`), без него — системный
`/var/backups/nas-os` (эфемерно, панель предупреждает).

### 2. Дизайн-система (весь новый UI обязан следовать)
Токены — CSS-переменные, тема через `:root[data-theme]` + `@media prefers-color-scheme`.
- НЕ использовать солид-цвета (`#hex`, `var(--bg)`, `var(--surface)`) как заливку карточек/панелей
  ВНУТРИ окон — только стекло `--glass`/`--card`. `var(--bg)` (сплошной) = ТОЛЬКО рабочий стол/body.
- **Elevation в тёмной теме = белый слой с прозрачностью** поверх материала (не осветление того же цвета).
- **Активные табы/сегменты/сайдбары — «белая фишка»**: `background:var(--sel)` + акцентный ТЕКСТ +
  `box-shadow:var(--sh-sm)`. НЕ заливать активное солид-акцентом.
- **Адаптивные поверхности**: `applySettings()` считает фактическую яркость фона каждой поверхности
  (menubar/dock/`.wdg`/`.win`/`.dialog`/`.menu`) и ставит scoped-переменные на `:root`:
  `--{mb|dock|wdg|win}-bg/-bf/-fg/-dim/-line/-accent/-good/-warn/-danger/-track`. Цвета текста/акцента
  подгоняются по контрасту через `accentAdj(hex, effL)` (WCAG). Новый элемент внутри поверхности —
  бери `var(--good/--warn/--danger/--track/--accent)` (они уже контрастно-подогнаны), НЕ хардкодь hex.
- **Профили тем**: все стилевые настройки (`THEMED_KEYS`) РАЗДЕЛЬНЫ для light/dark
  (`SET.themeProfiles`). Новую стилевую настройку — обязательно в `THEMED_KEYS`.
- Иконки — `svg(name,size)` (Lucide-подобные пути в объекте `P`/`I`). Тултипы — `tipHTML()`/`.tip`
  (тёмный пузырь, НЕ на `--ink`). Кнопки `.btn`/`.iconbtn`, сегменты `.seg`, тумблеры `.tgl`,
  диалоги `#scrim`+`.dialog`, поповеры бара `mbPop()` (класс `.mbpop`).
- Прежде чем добавлять окно/компонент — переиспользуй существующие классы/хелперы.

### 3. Язык интерфейса — ТОЛЬКО английский (рантайм-i18n СНЯТ)
UI пишется СРАЗУ по-английски — это единственный язык интерфейса. Словаря `web/i18n.js`
и рантайм-перевода БОЛЬШЕ НЕТ: их выпилили осознанно (ветка `i18n-english-only`, влита в
main — коммит «снос рантайм-i18n — english-only»). Что осталось как заглушки для
совместимости старых call-site'ов, а НЕ как живой слой перевода:
- `nasTr` в `desktop.html`/`setup.html`/`screen.html` — тождественная функция
  (`window.nasTr=function(s){return s}`), `NAS_LANG="en"` захардкожен.
- `tr()` в `nas-web.py` — identity-pass (`return text`), оставлен только чтобы
  серверные call-site'ы (Pushover, лейблы экрана) не падали.
Правила для нового кода: **никаких русских UI-строк** — пиши по-английски. Оборачивать
новую строку в `nasTr(...)` не нужно (заглушка ничего не делает; существующие обёртки не
трогай — они безвредны). Строки `meta.json` в каталоге приложений — тоже английские.
**НЕ возвращай рантайм-словарь/второй язык без явной просьбы пользователя.**

**Комментарии в коде — ПО-АНГЛИЙСКИ.** Старые русские не переводим массово (огромный diff,
шум в `git blame`), но всё новое и всё, что правишь по ходу, комментируй по-английски —
файлы переходят постепенно. Если когда-нибудь понадобится массовый перевод комментариев —
только через токенизаторы (`tokenize`+`ast` для питона; сканер состояния
строка/шаблон/regex для JS и shell), инвариант: код без комментариев обязан остаться байт
в байт прежним (наивный `sed` по `#`/`//` ломает URL, `${VAR#...}` и регулярки).

### 4. Адаптив (десктоп НЕ трогать — всё под media-queries / `isPhone()`)
Флаги: `isPhone()` (≤640), `isTablet()` (641–1024), `isTouch()` (pointer:coarse).
- Планшет+телефон (≤1024): окна **полноэкранные** (`.win{inset:40px 0 …dock 0 !important}`),
  `openWin` пропускает drag/resize; **один док внизу** — зарезервированная полоса с гориз. скроллом
  (контент резервирует его высоту, не прячется под ним); вертикальные сайдбары окон
  (`.set-nav`, `.dm2`) → горизонтальные «таблетки»/лента; тап-таргеты крупнее, инпуты 16px.
- Кнопка «назад» в шапке окна (`.wback`) → `goHome()`. `.wall-refresh` и т.п. скрыты на ≤1024.
- Не полагайся на `!important`-инсет против инлайн-стилей без проверки специфичности (был баг:
  `body.dock-left .desk{bottom:0}` перебивал мобильный отступ по специфичности).

## Кэш / доставка (важно для мобильных)
HTML отдаётся `Cache-Control: no-store` (мобильные при `no-cache` держали старую оболочку).
`web/sw.js` — network-first, навигация только из сети; при правках, если телефон видит старое —
сбросить SW (закрыть вкладку/PWA и открыть заново). При изменении shell-кэша поднимай `CACHE` (v↑).

## Ключевые грабли
- **USB-SATA мосты (UAS)** отдают диск как `ID_BUS=ata`, а не `usb` → udev-правила матчить по
  `ENV{ID_USB_DRIVER}=="?*"` (ловит usb-storage и uas), НЕ по `ID_BUS==usb`.
- **USB-диск уходит ОФЛАЙН посреди бэкапа → ext4 в аварийный read-only.** 2026-07-12 18:46:
  Ugreen (RTL9210) + Seagate ST4000LM024 (2.5" **SMR**): команда записи висела 68 с (SMR-диск
  ушёл во внутреннюю перетасовку), ядро на 30-й секунде (дефолтный таймаут SCSI) объявило
  ошибку → `Device offlined - not ready after error recovery` → `Remounting filesystem read-only`.
  Симптом в панели обманчив: прогон обрывается, а СЛЕДУЮЩИЙ красит ВСЕ папки красным — rsync не
  может даже `readdir` приёмника (`Input/output error (5)`), выглядит как «бэкап всё сломал».
  Диагноз — `dmesg` (`cmd_age=68s`, `offlined`) + `mount` (флаг `emergency_ro`). SMART при этом
  ЧИСТЫЙ (Reallocated/Pending/Uncorrect/CRC = 0, error log пуст) — носитель ни при чём, виноват
  таймаут. Лечение — udev-правило в `install_automount`: `device/timeout` = 180 с для USB-дисков.
  После такого обрыва обязательно `umount` + `e2fsck -fp` (журнал оборван).
- **Таймаута мало: UAS добивает диск сам. UAS ВЫКЛЮЧЕН ВСЕГДА с 2026-07-12** (`install_uas_off()`).
  Через 2 часа после лечения таймаутом — второй обрыв бэкапа, уже НЕ по таймауту (180 с
  применились). В 19:38 по диску пошёл `smartctl` (ATA pass-through, `opcode=0x85` — smartd
  и Scrutiny) ПОКА rsync писал; команда зависла, и `uas_eh_abort_handler` не смог отменить её
  в одиночку → `uas_eh_device_reset_handler` → reset ВСЕГО usb-устройства → оборваны все
  inflight-записи → офлайн → `emergency_ro`. Суть: **error recovery у UAS ресетит устройство
  целиком**, у usb-storage (BOT) зависшая команда падает одна. BOT «медленнее» только на бумаге:
  потолок и так гигабитная сеть (118 МБ/с) и сам HDD (~120 МБ/с).
  Одной глобальной ручки НЕТ: **`uas` вкомпилен в ядро Pi** (`modinfo uas` → `(builtin)`), поэтому
  `blacklist uas` в `modprobe.d` — пустышка; единственный рычаг `usb-storage.quirks`, и он требует
  явный VID:PID, шаблонов не понимает. Старая опция «Отключить UAS» была ловушкой: она собирала
  VID:PID только тех дисков, что воткнуты В МОМЕНТ её запуска, — Ugreen подключили позже, флаг
  горел «включено», а мост все эти месяцы жил на UAS. Поэтому опции больше НЕТ (ни в визарде, ни
  в мастере, ни в панели), а список сам себя поддерживает: udev-хук `nas-uas-off.sh` ловит любой
  мост с `ID_USB_INTERFACES ~ ":080662:"` (= умеет UAS; у флешек-BOT только `:080650:`), дописывает
  его в `/sys/module/usb_storage/parameters/quirks` И в `cmdline.txt`, затем переподнимает
  устройство (`authorized` 0→1) — оно перепривязывается к usb-storage без ребута. Живой параметр
  правится на лету, так что чинить можно и работающий бокс. Любой список «поддерживаемого железа»,
  собранный один раз, протухнет — собирай его по событию.
- **Дочерний процесс nas-web умирает при рестарте службы.** systemd убивает ВСЮ cgroup службы,
  поэтому `sudo systemctl restart nas-web` (наш обычный цикл разработки!) молча уносил sshfs-демоны
  SSH-серверов ФМ, оставляя мёртвые точки монтирования. Симптом обманчив: `mount` показывает маунт,
  а любое обращение — `Transport endpoint is not connected`, ФМ пишет «not a directory».
  Усугубляло то, что `_remote_mounted()` считал маунт живым по факту наличия в `/proc/mounts` →
  панель отвечала «уже смонтировано» и отказывалась перемонтировать. Лечение: **долгоживущий
  процесс — в СВОЙ transient-юнит** (`systemd-run --unit nas-remote-<id> --collect`, `sshfs -f`,
  `Restart=on-failure`, `ExecStopPost=umount -l`) — переживает рестарт панели, а упавший sshfs
  systemd поднимает сам. Живость маунта проверять `statvfs` (на битом FUSE ядро отвечает ENOTCONN
  сразу, без похода на сервер), а НЕ грепом `/proc/mounts`. Пароль — через `--setenv` (окружение
  юнита читает только root), НЕ в argv (`/proc` виден всем); `StandardInputText` транзиентному
  юниту задать нельзя — systemd-run его не принимает.
- **Бэкап: у задачи свой `dest`, и он не следует за общей папкой-приёмником.** Каждая задача хранит
  `dest`, посчитанный в момент добавления источника. Смена «общей папки-приёмника» меняла только
  `dest_base`, а прогон идёт по `dest` задачи → rsync молча лил в СТАРУЮ папку, пока панель
  показывала новую. Лечение: в режиме единой папки `dest` — чистая функция от (`dest_base`, `src`),
  и `nb_save()` выводит его САМ (`_nb_dest_for`, то же правило, что `destFor` в UI), не доверяя
  копии из запроса. Общее правило: если значение выводимо — выводи его на сервере, а не храни
  копию, которая разъедется с источником.
- **Роль по умолчанию в диалоге форматирования = «Данные» → флешка молча уходит в ПУЛ.**
  2026-07-12: пользователь форматировал внешний USB-диск, роль не трогал — диск стал веткой
  mergerfs (`/mnt/disk3`), попал в fstab и в пул. Вынь такой диск — часть `/mnt/storage`
  исчезнет. Лечение: у USB-диска (`tran=="usb"`) роль по умолчанию «Съёмный», а выбор «Данные»
  для съёмного диска показывает, чем это кончится. Разбор завала: строку из `/etc/fstab`,
  `umount`, `rmdir /mnt/diskN`, затем `nas-wizard.sh api mergerfs` — он пересобирает ветки из
  фактически смонтированных `/mnt/disk*` (`mounted_data_disks`), руками юнит не правь.
- **FAT32 на приёмнике бэкапа = гарантированный обрыв.** Потолок файла 4 ГиБ — rsync падает
  с `File too large (27)` и роняет ВСЮ задачу (не «пропускает файл»). Плюс vfat без `iocharset`
  монтируется как **ascii**, и любое имя с кириллицей падает с `mkdir … Invalid argument (22)`.
  Автомонтирование теперь даёт vfat `iocharset=utf8`, а панель предупреждает про 4 ГиБ ДО
  запуска. Приёмник бэкапа — только ext4 (exfat, если диск нужен и на Windows/Mac).
- **Профиль бэкапа в API передаётся ключом `p`**, а не `profile`/`id`. Ошибёшься — запрос уйдёт в
  профиль по умолчанию (последний сохранённый) и перепишет ЕГО настройки. Проверено на себе.
- **`include` в `smb.conf` ставить ТОЛЬКО в самый КОНЕЦ файла (top-level), НЕ после `[global]`.**
  `include` вклеивается текстом буквально: если он стоит внутри `[global]`, а инклуд-файл содержит
  `[global]`+секции шар, то все глобальные параметры smb.conf, идущие ПОСЛЕ строки include,
  припишутся к последней шаре инклуда (`testparm`: «Global parameter … found in service section!»)
  и потеряются из global. Проверено `testparm` 2026-07-20. Поэтому и панельный
  `include = /etc/samba/nas-shares.conf`, и `tm_ensure_include` (Time Machine — там был этот баг,
  исправлен) дописываются В КОНЕЦ, с нормализацией старого кривого размещения (снять любую строку

monitor_loop (перегнать, если последний drill старше `drill_every` дней). Один чип на карточке

**Kopia: добраны неиспользованные возможности движка (2026-07-25).** Полная сверка нашего кода
с CLI kopia 0.23.1 (`--help-full` по каждой группе) показала, что по смыслу покрыт весь обычный
цикл, но восемь содержательных вещей не были задействованы. Сделаны все, кроме сознательно
отложенных (см. конец блока).
- **Лимит скорости — на ЛЮБОЙ приёмник** (`repository throttle set`). В CLAUDE.md и в UI раньше
  стояло «у kopia НЕТ своего тротлинга, cloud-only через `RCLONE_BWLIMIT`» — **это было неверно**:
  throttle работает на всех бэкендах, включая filesystem, и хранится В РЕПОЗИТОРИИ (переживает
  переустановку). `RCLONE_BWLIMIT` из `_kp_env` убран, чтобы не было двух ограничителей.
  `kp_opts` получил `dnlimit_kb` (скачивание: restore/verify/просмотр); `kp_throttle_args/push/get`,
  push на каждый `kp_opts_set` и на каждый `_kp_ensure_connected` (свежий connect заново
  утверждает наши капы). API `POST /api/kopia/dest/throttle` — читает то, что репозиторий реально
  хранит. Теперь можно придушить снапшот на USB-мост, а не только в облако.
- **Хуки до/после снапшота** (`policy set --before/--after-snapshot-root-action`) — ПРАВИЛЬНЫЙ
  способ бэкапить БД: дамп в `before`, уборка в `after`, вместо копирования живых файлов базы.
  Сущность Backup: `hooks {before,after,mode:essential|optional,timeout}`. **ГРАБЛЯ №1:** kopia
  НЕ пускает action через шелл — она режет строку по пробелам на path+args, и пайплайн
  `pg_dump … | gzip > f` превратился бы в мусор. Поэтому панель материализует команду в скрипт
  `/etc/nas-os/kopia/hooks/<bid>-{before,after}.sh` (0700, root, с `#!/bin/sh` и `set -e`) и отдаёт
  kopia ПУТЬ — есть полный шелл и он же аудируем на диске. **ГРАБЛЯ №2:** actions выполняются
  только если у КЛИЕНТА стоит `enableActions` — иначе kopia молча их пропускает; `--enable-actions`
  добавлен в `_kp_repo_args`, а старым конфигам флаг дописывает `_kp_ensure_actions` правкой
  derived-JSON (дешевле реконнекта, для облака — без сети). Пустая строка в
  `--before-snapshot-root-action` СНИМАЕТ хук. Скрипты удаляются вместе с заданием
  (`_kp_forget_runs`). UI: секция «Before & after» в настройках задания (мода «Stop the backup» =
  essential — для дампа, без которого снапшот бесполезен).
- **Правила чтения** (`rules` у Backup → policy): `--one-file-system` (не уходить в примонтированное
  внутри источника), `--ignore-cache-dirs` (CACHEDIR.TAG, по умолчанию вкл.), `--max-file-size`
  (**ГРАБЛЯ: хочет БАЙТЫ, «1GB» не парсит**), `--ignore-file-errors`/`--ignore-dir-errors` (в UI
  честно сказано, что это делает «успешный» бэкап тихо неполным). Секция «What gets read».
- **Закрепление точки** (`snapshot pin --add/--remove keep`) — ретеншен никогда не съест помеченную.
  **ГРАБЛЯ: pin ПЕРЕПИСЫВАЕТ манифест, id снапшота МЕНЯЕТСЯ** — после pin нельзя переиспользовать
  прежний id, надо перечитать список (в Explorer это `exReload(tc, ts)`: ищем ту же точку по
  ВРЕМЕНИ, а не по id, и остаёмся в той же папке). `kp_snapshots` отдаёт `pins[]`; в таймлайне
  звезда-тумблер, у закреплённой точки корзина заблокирована, тик обведён жёлтым.
- **Сравнение точек** (`kopia diff <oid1> <oid2>`) — «что изменилось» на уровне файлов, как
  «What changed» у Mirror. `kp_snap_diff` парсит `added/removed/changed`, отбрасывая построчный шум
  «sizes differ / modification times differ», итоги берёт из ЗАВЕРШАЮЩЕЙ строки JSON; кап 400 путей

**Kopia: репозиторный СЕРВЕР — чужие машины бэкапятся В этот бокс (2026-07-25).** Вкладка
**Server** в приложении Kopia, два пейна (`srvPane`): **Settings** (переключатель) и **How to
connect** (готовые команды с ПОДСТАВЛЕННЫМ адресом, отпечатком и логином — то, что никто не
запоминает). Смысл: у нас была только модель «бокс сам забирает/бэкапит», ноутбуку приехать было
некуда; SMB-шара не даёт ни версий, ни ретеншена, Syncthing синхронизирует, а не версионирует.
- **Модель.** Один сервер = ОДИН репозиторий (`server.dest` в kopia.json). Клиент делает
  `kopia repository connect server --url=https://бокс:51515 --server-cert-fingerprint=…` и логинится
  СВОИМ `login@hostname` + собственным паролем: пароля репозитория он не знает и к хранилищу
  (pcloud/диск) доступа не имеет. Дедуп общий с нашими бэкапами — один и тот же файл с трёх машин
  хранится один раз (проверено: два клиента с одинаковой папкой дали ОДИН root-oid).
- **TLS обязателен** для не-loopback, CA у домашнего бокса нет → свой самоподписанный сертификат
  (`/etc/nas-os/kopia/server/{cert,key}.pem`, 0600, SAN = LAN-IP + hostname + hostname.local +
  localhost, openssl, 10 лет), клиент ПИНИТ его отпечаток. Отпечаток = `sha256(DER)`, считаем сами
  из PEM (`_kp_srv_fingerprint`, base64→hashlib) — не дёргая openssl. Сертификат создаётся ЗАРАНЕЕ
  при первом открытии вкладки, чтобы инструкция была без placeholder'ов. **Он в СЕКРЕТНОЙ секции
  бэкапа настроек** (`nasbackup`, префикс `etc/nas-os/kopia/server/`): потеряешь — все клиенты
  откажутся подключаться, пока не перепинишь руками (та же логика, что у key.pem Syncthing).
- **ГРАБЛЯ (стоила провального прогона): пользователь, добавленный при ЖИВОМ сервере, не работает
  сразу.** kopia честно пишет «take effect in 5-10 minutes or when the server is restarted», клиент
  до этого получает `PermissionDenied: access denied for user@host` — читается как неверный пароль.
  Штатный способ — `kopia server refresh` через control API, но он требует пароль, а **сервер НЕ
  читает `KOPIA_SERVER_CONTROL_PASSWORD` из окружения** (проверено: и с верным, и с неверным env
  ответ `401 Unauthorized`) — только argv, то есть секрет в `/proc/*/cmdline`. Поэтому control API
  выключен совсем (`--no-control-api`, плюс `--no-ui` — UI у нас свой), а `kp_srv_refresh()` просто
  ПЕРЕЗАПУСКАЕТ юнит: детерминированно и без секретов. Прерванную заливку клиент возобновляет сам.
- **Пароль пользователя тоже не через argv.** `--user-password` кладёт его в командную строку, а
  `--ask-password` отказывается читать из пайпа («inappropriate ioctl for device») → `_kp_srv_pw_set`
  ведёт его ДВА промпта («Enter new password…», «Re-enter password for verification:») через **pty** —
  тот же приём, что для прогресса снапшота. Открытый пароль зеркалим в kopia.json, чтобы показывать
  в UI (как `smb-users.json`).
- **Живучесть.** Свой транзиент-юнит `nas-kopia-server` (`Restart=on-failure`), потому что рестарт
  панели убивает её cgroup; `_kp_srv_tick` в `_kopia_tick` поднимает сервер, если `enabled`, а юнита
  нет (ребут, краш, переустановка — kopia.json приезжает с бэкапом настроек, этого достаточно), при
  неудаче — событие `kp_err` с кулдауном. Порт: открывается в ufw при включении, закрывается при
  выключении, И добавлен в `_ufw_managed_ports()` — `ufw_autosync` держит его открытым сам.
- **Гарды:** приёмник, который отдаёт сервер, нельзя забыть, пока сервер ВКЛЮЧЁН (а если выключен —
  ссылка просто снимается, это было отдельной находкой: гард сначала блокировал удаление всегда);
  включение без выбранного репозитория и с портом вне 1024-65535 отклоняется; смена порта/приёмника
  на живом сервере сперва гасит старый (иначе прежний порт остался бы открытым в ufw); имя
  пользователя строго `login@hostname` (regex), пароль 4-128.
- **Чужие снапшоты видны как свои:** `kp_snapshots` теперь отдаёт `user`/`host` (ДВЕ машины могут
  иметь ОДИН путь — без владельца Explorer слепил бы их в одну ложную историю), Explorer листает,
  сравнивает, скачивает и восстанавливает их наравне с нашими. Ретеншен клиентских папок задаётся НА
  КЛИЕНТЕ — в UI это сказано прямо, чтобы не искали настройку у нас.
- **Disaster card** получила секцию «Other machines backing up into this box»: отпечаток, порт,
  логины с паролями и команда переподключения — после катастрофы клиентам нужен именно отпечаток.
- API: POST `/api/kopia/server` (status, `deep:1` — плюс список клиентов из репозитория),
  `server/set`, `server/restart`, `server/user` (add/set/remove), `server/cert` (пересоздать).
  CSS-кит вкладки: `.kp-cmd` (блок команды + Copy), `.kp-copyv` (клик-копирование значения),
  `.kp-stepn` (номер шага).
- **Проверено:** live e2e 23/23 на ИЗОЛИРОВАННОМ репозитории — сервер включился через реальный
  `kp_srv_set`, зарегистрирована машина, НАСТОЯЩИЙ клиент (свой config+кэш, другой user@host)
  подключился и залил снапшот ЧЕРЕЗ сервер, панель увидела его с владельцем и пролистала, неверный
  пароль отклонён, отпечаток совпал с `sha256(DER)`, ключ 0600, секретов в argv нет, гарды и
  авто-подъём после «краша» работают; фикстуры и тестовый приёмник вычищены, боевые сущности целы.
  **CDP 42/42, ноль JS-ошибок** (оба пейна, гард «нельзя включить без репозитория», диалог машины с

**Kopia: кэш ответов, адресуемых object id — просмотр облачного репозитория стал мгновенным
(2026-07-25).** Серверный режим для этого НЕ нужен и не нужен вовсе: панель ходит к репозиторию
своим CLI, а не через сервер, поэтому включение сервера на скорость просмотра не влияло бы никак
(это два независимых процесса, каждый открывает репозиторий сам). Сделано дешевле и без служб.
- **Идея:** object id у kopia содержательный, значит папка с таким id НИКОГДА не меняет содержимое.
  Ответ «листинг oid/rel» (а также «поиск по oid+запрос» и «diff двух oid») можно хранить ВЕЧНО —
  инвалидации не существует по определению, нет ни TTL, ни риска устаревания. Дорога не сама
  выборка: КАЖДЫЙ промах открывает репозиторий, а для облака это ещё и запуск моста
  `rclone serve webdav`.
- **Реализация:** sqlite-стор `panel-answers.db` ВНУТРИ папки кэша приёмника (`_kp_ans_db/get/put`,
  ключи `ls:`/`find:`/`diff:`), поэтому «Clear local cache» и удаление приёмника его сносят
  автоматически. Капы `KP_ANS_MAX_ROWS`=20000 / `KP_ANS_MAX_BYTES`=64 МБ, при переполнении
  выбрасывается наименее давно использованная четверть (`ts` обновляется при чтении). Оборванный

**Приложение «Immich Standby» — тёплый резерв чужого Immich (2026-07-26).** Решение пользователя:
не проверка ради проверки и не живая копия 24/7, а тёплый резерв. Ночью свежайший дамп заливается
в ПОСТОЯННУЮ базу здесь, контейнеры при этом стоят; заливка сама себе проверка. «Поднять» = старт
стека на готовой базе (минута-две вместо десяти).
- **Библиотека монтируется НАЛОЖЕНИЕМ (overlayfs)**: lower = копия в бэкапе (только чтение),
  upper/work = черновой слой в `<work>/lib-upper`. Immich обязан писать в `UPLOAD_LOCATION`
  (превью, перекодировка) — и пишет в черновик, а бэкап под ним не меняется ни на байт.
  Проверено отдельно, в том числе с ПРОБЕЛОМ в пути (`/home/Photos Immich`) — `mount -o
  lowerdir=…` пробел переживает, разделитель только запятая. При Stop черновик стирается.
- **Резерв не должен воскресать сам:** копия рецепта правится на лету — свой порт (2284, чтобы
  не столкнуться с настоящим Immich), имена контейнеров `immich_sb_*` (в рецепте они жёсткие) и
  `restart: "no"` вместо `unless-stopped` (иначе резерв поднимался бы после каждого ребута).
- **Ночной цикл** (`_imsb_tick`, слот-паттерн): пропускается, если тот же дамп уже восстановлен,
  если стек поднят или если прогон уже идёт. Драйвер `immich-standby-refresh` в транзиент-юните
  `nas-immich-standby`: поднимает ОТДЕЛЬНЫЙ Postgres-контейнер на папке резерва (стек не при чём),
  ждёт трижды `select 1` (грабля initdb), `DROP DATABASE`+`CREATE` (полу-применённый дамп поверх
  вчерашнего — это ни вчера, ни сегодня), заводит роли из дампа, грузит потоково через `gzip`,
  считает ассеты и пользователей. Пустая база после заливки = ошибка. **Просадка ассетов >10 %
  относительно прошлой ночи — отдельное уведомление**: библиотека не худеет на десятую часть за
  ночь. Событие каталога `imsb_fail`.
- **Приложение** `__immichsb` «Immich Standby», иконка — родной логотип Immich с тёмным бейджем
  питания («копию можно включить»). Одна страница: вердикт-hero (нет бэкапа / нет дампа / ни разу
  не готовили / запущено / последняя заливка упала / готово, но дамп старый / готово), четыре
  плитки (версия, возраст дампа, фотографий в копии, когда обновляли), тумблер ночной заливки +
  время + порт, пути, история последних заливок. Кнопки «Bring it up» / «Stop» с подтверждением.
- **ГРАБЛИ, найденные на живом прогоне** (все исправлены): (1) `restart: "no"` в копии рецепта
  спасает от воскрешения после ребута, но ЛОМАЕТ первый старт: восстановленный Postgres
  проигрывает WAL, сервер Immich встречает «the database system is starting up» (57P03), падает и
  больше не поднимается. Лечение — не рестарты, а ПОРЯДОК: `up -d database`, ждать трижды

- **АУДИТ Immich Standby «что если» (2026-07-26): 33/33 зелёные, семь находок исправлено.**
  Прогон — `t_audit_imsb.py`: НАСТОЯЩИЙ Postgres, настоящий дамп, свой каталог/контейнеры/конфиг
  (боевой не трогается, проверяется ассертом в конце). Проверялся не счастливый путь (он уже
  доказан живьём), а плохие дни: битый gzip, ломаный SQL, пустая база, урезанный дамп, убитый
  посреди работы драйвер, пропавший диск, два действия одновременно, ребут при `keep_up`.
  (1) **Сторож «копия усохла» разоружался после КАЖДОЙ неудачной ночи**: прошлое число фотографий
  бралось из `last`, а туда пишется и запись-ошибка (без счётчика) → следующий прогон сравнивать
  было не с чем, и урезанный вдвое дамп проезжал молча. Теперь `prev` ищется по ИСТОРИИ — последняя
  запись, которая реально приземлилась (`assets>0`, не `kind:check`). ПРАВИЛО: «предыдущее
  значение» для сравнения бери из последнего УСПЕХА, а не из последней записи. (2) Пароль БД уходил
  в `docker run -e` → был виден в `/proc/*/cmdline` любому пользователю; теперь `--env-file` 0600
  (как у sshfs/kopia-драйверов). (3) Если переименование `immich_new`→`immich` падало ПОСЛЕ сноса
  старой базы, обработчик ошибки сносил и новую — то есть уничтожал единственную оставшуюся копию,
  сообщая при этом «данные на месте». Теперь `fail(..., keep_new=True)`: база сохраняется, в тексте
  сказано, как её вернуть; плюс перед вторым `ALTER` рвутся чужие соединения. (4) Еженедельная
  сквозная проверка не могла выключить копию за собой: `imsb_down` отказывает, пока активен юнит
  заливки, а проверка сама живёт ВНУТРИ этого юнита → копия оставалась поднятой, а поднятая копия
  отменяет все ночные заливки. Внутренний вызов теперь `force=True` (и честно пишет в шаги, если
  выключить не удалось). (5) Сторож `keep_up` вызывал `imsb_up()` ПРЯМО в monitor-нити (это минуты
  ожидания WAL-реплея) — вынесен в свой поток с флагом «уже идёт»; в monitor-нити висят термозащита,
  планировщики и health. (6) Смена папок/порта на ЖИВОЙ копии отклоняется: они запечены в поднятых
  контейнерах, и «Stop» после такой правки искал бы compose в новом месте, оставив контейнеры
  сиротами и оверлей смонтированным. (7) Порт валидируется (1024-65535, число) — молчаливый откат
  к 2284 читался как «сохранение не сработало». Проверено через РЕАЛЬНЫЙ HTTP (сессия минтится
  записью токена в `sessions.json` + рестарт, потом ОТЗЫВАЕТСЯ): все шесть веток отвечают своим
  текстом, боевой конфиг после прогона байт-в-байт прежний. ПОРЯДОК ПРОВЕРОК в ручке: сначала
  ФОРМА присланного (число ли порт, абсолютен ли путь), потом СОСТОЯНИЕ («копия запущена») —
  иначе опечатка в порту под живой копией отвечает «сначала остановите копию», то есть врёт,

**Приложение «Syncthing» — СИСТЕМНЫЙ сервис, не контейнер (2026-07-24).**
Непрерывная двусторонняя синхронизация с ноутбуками/телефонами/другими боксами. Ставится в
АВТО-БАЗЕ (`install_syncthing` в `stage_system_apply`, `api syncthing` / `api syncthing-update`).
- **Источник — ОФИЦИАЛЬНЫЙ apt-репозиторий Syncthing**, не Debian: в trixie лежит 1.29.5 (мажор
  назад), в `apt.syncthing.net` компонент `stable-v2` даёт 2.1.2. Ключ `syncthing.net/release-key.gpg`
  в `/etc/apt/keyrings/`, строка источника с `arch=` (на RPi OS 64-бит armhf — чужая архитектура,
  без пина apt тянет индекс, из которого никогда не поставит). Дальше apt обновляет сам.
- **Свой юнит `nas-syncthing.service`** (не пакетный `syncthing@user`): home `/var/lib/syncthing`,
  от root — синхронизируемые папки в пуле принадлежат кому угодно (та же логика, что
  `force user = root` у Samba). Пакетный `syncthing@root` глушится (`disable --now`), иначе второй
  экземпляр из другого конфига. **ГРАБЛЯ:** syncthing ПАДАЕТ на старте, если не определён `$HOME`
  (`panic: Failed to get user home dir`) — он резолвит домашнюю папку в init пакета, ДО разбора
  `--home`, а у юнита своего HOME нет → `Environment=HOME=/root` обязателен. Плюс
  `STNODEFAULTFOLDER=1` (не создавать `~/Sync`), `SuccessExitStatus=3 4` (3 = рестарт из GUI, 4 =
  апгрейд — перезапускает systemd).
- **GUI — только loopback, панель его ПРОКСИРУЕТ** (`/syncthing/*` → `127.0.0.1:8384`,
  `_st_serve`/`st_proxy` в nas-web.py) за своим логином, поэтому в локалке нет неавторизованной
  админки и отдельный пароль не нужен. Работает это потому, что весь SPA Syncthing
  **относительный** (`urlbase = 'rest'`, `assets/…`, `vendor/…`) и **без websockets** (только
  long-poll `/rest/events`), а окно панели — тот же origin, что удовлетворяет их
  `X-Frame-Options: SAMEORIGIN` (прямой iframe на `:8384` был бы заблокирован). Прокси добавляет
  заголовок `X-API-Key` из config.xml — это и авторизует, и снимает их CSRF; хоп-бай-хоп заголовки
  и `Accept-Encoding` срезаются, `Location:/…` переписывается в `/syncthing/…`. Ради прокси
  добавлены `do_PUT/do_DELETE/do_PATCH/do_HEAD` (`_st_only`) — свой API панели говорит только
  GET/POST. Таймаут апстрима 180 с (их long-poll — 60 с).
- **Настройки → Syncthing** (`syncthingTab`): состояние службы + Restart/Update, device ID (Copy),
  тумблер **«Reachable on the local network»** (`st_set_lan` — правит адрес через ИХ REST
  `PUT /rest/config/gui`, НЕ редактированием config.xml под живой службой: она перезаписывает файл
  сама; плюс открывает/закрывает порт в ufw и честно предупреждает, что своего пароля у GUI нет),
  тумблер **«Match the panel's theme»** и ручной выбор темы.
- **Тема Vellum** (github.com/pelinoleg/syncthing-vellum) ставится обе (light+dark) в
  `<home>/gui/`, активной делается `vellum-light` — но ТОЛЬКО пока в конфиге стоит `default`
  (осознанный выбор пользователя переустановка не затирает). Дальше тему ведёт ПАНЕЛЬ:
  `SET.stFollow` (по умолчанию вкл., НЕ в `THEMED_KEYS` — это одна настройка про обе темы, а не
  значение на тему) + `syncthingFollowTheme()` в ветке смены темы `applySettings()` и разово на
  загрузке. Сервер (`st_set_theme`) при совпадении темы НИЧЕГО не пишет и отвечает
  `unchanged:true` — иначе каждая загрузка панели переписывала бы их конфиг; при реальной смене
  открытое окно перезагружается (`stReloadWindow`), иначе в нём остаётся старый CSS.
- **Иконка** — родной логотип (RAW_LOGOS.syncthing, дал пользователь). Оптический баланс:
  диск full-bleed, поэтому `translate(-8.1,-8.1) scale(0.684)` (≈125 % бокса 64) — на глаз в один
  вес с Cron/Kopia/Disk usage; мерил шириной «чернил» через CDP (`getBoundingClientRect` по всем

- **ufw**: открываются только порты синхронизации `22000/tcp+udp` и `21027/udp`; GUI-порт — только
  когда его сознательно выставили в локалку.
- **Бэкап настроек**: секция `syncthing` (секретная) — `config.xml` + `cert.pem` + `key.pem`.
  Identity бокса ЭТО и есть key.pem: потеряешь — NAS вернётся чужим устройством, и его придётся
  принимать заново на каждом пире. База индексов НЕ бэкапится (она пересобирается из файлов).
  При восстановлении файлы кладутся 0600 в 0700-папку и служба перезапускается (живой syncthing

**ГРАБЛЯ: «Stop» у резерва Immich не держался — сторож поднимал копию обратно (2026-07-26).**
Пользователь нажал Stop, через минуту копия снова работала, нажал ещё раз — то же. Виноват не
Stop, а `keep_up`: тумблер «держать копию включённой» — это ПОСТОЯННОЕ указание, и сторож в
`_imsb_tick` исполняет его раз в минуту, поэтому ручная остановка отменялась им же. Лечение:
`imsb_down(by_hand=True)` (только из ручки `/api/immich-standby/down`) СНИМАЕТ `keep_up` и
взводит backoff сторожа, диалог подтверждения об этом ПРЕДУПРЕЖДАЕТ заранее, а тост подтверждает
после; внутренние вызовы (еженедельная сквозная проверка, драйвер заливки) настройку не трогают.
ПРАВИЛО: если у режима есть сторож, исполняющий его автоматически, то ручное действие, обратное
режиму, обязано либо снять режим, либо быть отклонено с объяснением — молча проигрывать сторожу
кнопка не имеет права. Проверено 9 ассертами (by-hand снимает и сообщает, внутренний вызов не
трогает, сторож поднимает при включённом режиме и не трогает остановленное вручную, боевой конфиг
цел). Ночная заливка от снятого `keep_up` не страдает — она идёт при остановленной копии по
основному пути (заливка в саму базу вместо подмены `immich_new`).

**ГЛАВНАЯ ГРАБЛЯ ПЛАНИРОВЩИКОВ: пропущенный слот стоил ЦЕЛОГО ДНЯ бэкапа, молча (2026-07-26).**
Пользователь заметил сам: ежедневный прогон в 15:00 вчера был, сегодня нет, на часах 21:00.
Диагноз по журналу: `_nb_sched_tick` сравнивал `s["time"]` с ТЕКУЩЕЙ минутой (`%H:%M`), то есть
слот существовал ровно 60 секунд и только в памяти живого процесса. А `monitor_loop` начинается с
`_mon_wake.wait(60)` — свежий процесс МОЛЧИТ первую минуту, и лишь потом идёт по списку тиков
(`history_sample`, `monitor_tick`, `maintenance_daily`, `_smart_selftest_tick` — и только затем
планировщик). В тот день я сам правил панель и рестартовал её каждые 40-60 секунд подряд, в том
числе в 14:59:59 → 15:00:58 → 15:01:39: ни один процесс не дожил внутри минуты «15:00» до
планировщика. Никакого «догнать» не было, уведомления «прогон пропущен» тоже — расписание просто
теряло сутки. Ровно то же дал бы ребут, обновление или падение в неудачную минуту.
Лечение — `_nb_sched_last_due(cfg, now)` + ПЕРСИСТЕНТНЫЙ слот (`nas-backup-sched.json`,
`{профиль: "YYYY-MM-DD HH:MM"}`): тик спрашивает не «сейчас ровно 15:00?», а «когда этот профиль
БЫЛ должен последний раз и отработали ли мы тот слот». Пропущенный слот догоняется, если следующий
запуск ещё не ближе пропущенного (окно 12 ч для daily, 24 ч для weekly), и НЕ догоняется, если с
тех пор уже был реальный прогон (`_nb_last_real_run` — история + run-state, сухие прогоны не
считаются) или если профиль СОХРАНЁН позже слота (расписание, поставленное в 20:00, не обязано
задним числом отрабатывать 15:00). Персистентность заодно чинит противоположный риск: рестарт
ВНУТРИ той же минуты больше не может запустить прогон дважды. Дни перебираются через `localtime`,
а не вычитанием 86400 из штампа — на переводе часов это разошлось бы на час.
Плюс СОБЫТИЕ `nb_missed` (каталог монитора, prio 1, кулдаун 6 ч): слот, который пропущен И уже не
догоняется, сообщается В ТОТ ЖЕ ДЕНЬ. Раньше единственным сторожем был `nb_stale` с порогом в
СЕМЬ ДНЕЙ — ежедневный бэкап мог молча пропасть на неделю, и именно так сегодняшний пропуск нашёл
не бокс, а пользователь. ПРАВИЛО: у периодической задачи порог тревоги обязан быть соизмерим с её
ПЕРИОДОМ, а не выбран «на глаз»; для ежедневной задачи неделя тишины — это не порог, это отсутствие
контроля.
ПРАВИЛО для любого расписания в этом проекте: слот — это ИНТЕРВАЛ «должен был к моменту X», а не
минута-совпадение; и он обязан лежать на диске. У Kopia очередь `pending` уже была, у Mirror не
было ничего. Проверено 16 ассертами (выбор слота, включая DST-сутки и weekly-переход через
полночь; догон один раз; отказ догонять просроченное/уже отработанное/сохранённое позже) и живьём:
после рестарта тик сказал «the 2026-07-26 15:00 run was missed — starting it now, 381 min late» и
поднял настоящий прогон.
**Заодно: одна кривая запись в `sessions.json` роняла ВСЮ панель в цикл рестартов.** 26.07 15:55
